# Reproduce: how to build a 3-D site map (digital twin) of a heritage site in Blender

This guide explains, step by step, how to go from a Google Maps link to a 3-D site map in Blender: calibrated terrain, modelled structures and trees. It's written so another agent (for example Kiro CLI) can repeat the method for **any site**, such as Kellis Castle in Perak.

The method was developed on the **Penang War Museum** (Muzium Perang, Batu Maung, Penang), which is the worked example throughout. Its project folder, `penang_war_museum/`, holds the reference scripts and outputs. Each step says:
- what was done there,
- which script does it,
- what to change for a new site.

> Worked example origin O: the Penang War Museum gate front, **5.281400 N, 100.288800 E**.
> To start a new site, jump to **section 12** and make a folder next to `penang_war_museum/`, for example `kellis_castle/`.

## Folder layout
```
~/Desktop/blender/
├── reproduce.md               ← this guide (shared by all sites)
├── penang_war_museum/         ← worked example (reference implementation)
└── kellis_castle/             ← next site, same layout (see section 12)
```

## 1. Tools and conventions

### Software
| Need | Used |
|---|---|
| Blender | 5.x (`/Applications/Blender.app/Contents/MacOS/Blender` on macOS) |
| Python | the system `python3` for the non-Blender scripts (`fetch_srtm.py`, `fit.py`, `make_sitemap.py`, `terrain.py`) |
| Browser | a browser the agent can drive and screenshot (Google Maps / Street View) |
| Optional | Blender MCP (`uvx blender-mcp` + the add-on) for interactive modelling of hero structures |
| Assets | Poly Haven (CC0) models: trees, plants, props |
| Elevation | OpenTopoData public API, SRTM 30 m dataset |

### Always run Blender in the background
```bash
BLENDER=/Applications/Blender.app/Contents/MacOS/Blender
"$BLENDER" -b --factory-startup --python tools/<script>.py -- <args>
```
- `-b` = no UI, `--factory-startup` = ignore user prefs and add-ons, so results are reproducible.
- Arguments after `--` go to the script (`sys.argv[sys.argv.index("--") + 1:]`).
- This never touches a file the user has open in their own Blender.

### Safety rules baked into every script
- Scripts **refuse to overwrite** an existing output (`REFUSING to overwrite …`). To rebuild, move the old file to a backup folder first, then run again.
- Every saved file runs `bpy.ops.file.pack_all()` so textures travel with the `.blend`.
- Linked libraries use **relative paths** (`//site_structures/…`), so the project folder can be moved as a whole.
- All tool paths are relative to the tool's own location (`tools/` → `museum_survey/` → project root), so the project works wherever it lives.

### One coordinate frame for everything (the key idea)
Everything is placed in one local frame, so files line up when linked without any manual alignment.

| Item | Rule (PWM values) |
|---|---|
| Origin O | a fixed, easy-to-recognise ground point: the **front centre of the main gate**, 5.281400 N, 100.288800 E |
| ENU metres | `E = (lon − O_lon) × KE`, `N = (lat − O_lat) × KN` |
| Metres per degree | `KN = 110574` (latitude), `KE = 111320 × cos(lat) = 110847` at 5.28° N. **Recompute KE for your latitude.** |
| Blender model frame | `x = −E` (+x west), `y = −N` (+y south, into the site), `z` up, `z = 0` = ground at O |

> Why `x = −E, y = −N`? The first model (the gate) was built facing −y toward the road, which is north. Everything else was made to match it. For a new site you can choose `x = E, y = N` instead; just be consistent and write it at the top of the survey.

## 2. Step 1: Survey the site with Google Street View → markdown + screenshots

Goal: one markdown file that a modelling agent can read without opening a browser.

1. **Open the entry point** in Street View (for PWM, the gate). Read the **URL**: `@lat,lon,3a,75y,190h,90t` gives the camera latitude, longitude, heading (`h`) and pitch (`t`). Some URLs also contain an altitude like `71a`. Write it down; it's used in step 4.
2. **Walk the whole public route**, clicking forward one panorama at a time. At every stop:
   - Save a screenshot named `P<nn>_<what>_<lat>_<lon>_h<heading>.jpg` into `museum_survey/screenshots/`. Take several headings at important places (`P11`, `P11b`, …).
   - Record the camera lat/lon and altitude.
3. **Check user Photo Spheres** (blue dots) for spots without Street View, e.g. `P17*` (gun pit, 2017) and `P18*` (photo sphere, 2016). Note the year; sites change.
4. **Take satellite screenshots** at known zoom levels (see step 3 for why). Name them with the zoom altitude and centre, e.g. `SAT07_context_912m_center_5.2805_100.289.jpg`. Use the URL form `https://www.google.com/maps/@<lat>,<lon>,<NNN>m/data=!3m1!1e3`. Keep the **same browser window size** for all of them (PWM: 800 × 600 px screenshots).
5. **Collect reference material:** official site maps, sketch maps, display models, signboards (`REF01–REF04`). For PWM the museum's hand-drawn sketch map (`REF02`) gave all 37 numbered relics.
6. **Visitor photos** (Google Maps gallery) for areas Street View doesn't reach, saved as low-resolution captures in `screenshots/gallery/` with the date and credit. **Respect copyright:** if a website says "ask permission before using my photo", do not copy it. Describe what it shows and link to it.
7. **Write the survey markdown** (`penang_war_museum_survey.md`), with these sections (the PWM file is the template):
   1. Coordinate system (origin, ENU formula, model frame)
   2. Master table: ID (B01…, S1…), name, lat/lon, E/N, size, rotation, source, accuracy
   3. Detailed description of each structure: dimensions, materials, colours, details, screenshot references
   4. Known structures not captured
   5. Material and colour palette (approximate sRGB)
   6. Suggested modelling order and file names
   7. Screenshot index
   8. Site map and sketch-map comparison
   9. Built models (filled in as you go)
   10. Relic catalogue, sources

**Positioning a structure from Street View:** the camera position is known. Estimate distance and bearing to the structure from the heading of the view in which it is centred, then cross-check against the satellite screenshot. Accuracy is typically ±3–6 m. Put that in the "accuracy" column.

## 3. Step 2: Georeference the satellite screenshots

A Google Maps satellite screenshot taken from the URL `@lat,lon,NNNm` is centred on (lat, lon). At the browser size used, its scale is **linear in NNN**:

```
metres_per_screen_px = 0.2667 × NNN / 166
```

`0.2667 m/px at "166m"` was measured once from the Google scale bar at PWM's window size. **Measure it again for your window size**: take one screenshot, read the scale bar, then divide metres by pixels.

So any screenshot pixel (px, py) maps to:
```
E = E_centre + (px − 400) × s        (400, 300 = screen centre of an 800×600 capture)
N = N_centre − (py − 300) × s
```
Each satellite entry in the scripts is `(file, centre_lat, centre_lon, s, crop_box)`. The crop box cuts off the Google UI (search bar, buttons). PWM uses two layers: `SAT07` (912 m, wide context) and `SAT01` (228 m, the hill in detail).

Measure satellite-only buildings (`S1–S6`) directly in pixels with this mapping and add them to the master table.

## 4. Step 3: Fit the sketch map (`tools/fit.py`)

Most heritage sites have an illustrated visitor map that isn't to scale. PWM's sketch map had all 37 numbered relics, which Street View couldn't see.

1. Save the map image as `tools/sketch.jpg`.
2. Choose **at least 4–5 control points** visible in both the sketch (pixel x, y) and the survey (E, N). For PWM: ticketing (B03), cafeteria (S5), souvenir shop (B07), the gate (O) and the gun bay #25 (B17).
3. `fit.py` solves a **2-D similarity transform** (rotation + uniform scale + shift) by least squares using complex numbers: `w = a·z + b`, where z is the sketch pixel (y flipped) and w is E + iN.
4. It prints the scale, rotation and per-point residuals, plus two independent checks, then writes `transform.json` (`a` and `b`).

```bash
python3 tools/fit.py
```
PWM result: rotation −154°, 0.385 m per sketch pixel, residuals 6–30 m. **Report this accuracy (±30 m) on every sketch-derived item**, because illustrated maps distort.

For a new site: edit the `ctrl` list (name, sketch px, real E/N) and the `CHECK` list.

## 5. Step 4: Make the 2-D site map and the points CSV (`tools/make_sitemap.py`)

```bash
python3 tools/make_sitemap.py
```
It contains the site data as Python lists:
- `S`: surveyed and satellite structures (ID, name, E, N, size E, size N, rotation, shape, source, accuracy)
- `WALKWAY`: path centreline
- `SV_PATH`, `SV_BRANCH`: Street View camera tracks
- `SK`, `SK_NAMED`: sketch numbers and features in sketch pixels, plus their matched survey IDs
- `SATS`: georeferenced satellite layers

It writes:
- `penang_war_museum_sitemap_topview.svg`: satellite underlay, 20 m grid, structures, paths, sketch relics, legend, north arrow and scale bar. Convert it to PNG for sharing.
- `tools/overlay.svg`: the same map with the sketch at 55 % opacity, for checking the fit.
- **`penang_war_museum_sitemap_points.csv`**: one row per item, with columns `id, name, type, lat, lon, E_m, N_m, model_x, model_y, size_E_m, size_N_m, rot_deg_ccw, source, accuracy, sketch_match`. The `type` is one of `surveyed`, `satellite`, `sketch_relic`, `sketch_feature` or `path` (the `B09_i` walkway vertices).

> ⚠️ **PWM only:** the CSV was later corrected by hand (B12 renamed to #29 tunnel entrance, R36 moved to model (−32, 24), duplicate-relic notes). **Re-running `make_sitemap.py` will overwrite those corrections.** For a new site, put corrections into the lists in `make_sitemap.py` itself so it stays the single source.

**From here on, the CSV is the only source of positions.** Every Blender script reads it, so moving a structure means editing one row and rebuilding.

## 6. Step 5: Terrain elevation calibrated by Street View (`tools/fetch_srtm.py`, `tools/terrain.py`)

### 6a. Download SRTM
```bash
python3 tools/fetch_srtm.py                       # PWM defaults
python3 tools/fetch_srtm.py O_LAT O_LON E_MIN E_MAX N_MIN N_MAX STEP   # new site
```
- Samples SRTM 30 m from `https://api.opentopodata.org/v1/srtm30m` (bilinear) on a 25 m grid. PWM: E −350…450, N −330…245, so 33 × 24 points.
- Uses 100 points per request and waits 1.1 s between requests (public API limit), with retries.
- Writes `tools/terrain_srtm.json`.
- Update `KE` inside the script for your latitude.

### 6b. Calibrate it (`terrain.py`)
SRTM is a **surface** model: over forest it measures the canopy, which is 5–12 m above the ground. The fix:
1. List the Street View camera positions with their URL altitude: `SV = [(E, N, altitude), …]`. PWM has 20 points along the visitor route.
2. Ground truth = altitude − **2 m** (Street View camera height).
3. Residual at each point = ground truth − SRTM.
4. Spread the residuals with **inverse-distance weighting** (`w = 1/(d² + 25)`). Within `R_INFL = 60 m` of a Street View point, blend toward a **default canopy correction** (`DEFAULT_CORR = −10 m`, the mean residual on forested points).
5. Fade the correction out near the coast (`SRTM < 12 m`) so the shore stays at sea level.
6. `GATE_ASL = ground_asl(0, 0)`; `z_model(x, y) = ground_asl(−x, −y) − GATE_ASL`, so z = 0 at O. `SEA_Z = −GATE_ASL`.

```bash
python3 tools/terrain.py    # prints every SV point: ground vs model vs raw SRTM, plus key locations
```
PWM: all 20 checkpoints agree within 0.8 m. The gate is 68.6 m above sea level (ASL), so the sea sits at z −68.6. If you can't find altitudes in the URLs, skip the IDW step and use a constant canopy correction, but say so in the survey.

## 7. Step 6: Build each structure in its own .blend (`tools/pwm_lib.py`, `tools/build_structures.py`)

```bash
"$BLENDER" -b --factory-startup --python tools/build_structures.py -- <target> [out_dir]
# targets: gun_emplacement watchtower bunker amenities walkway courtyard barrack_blue satellite sketch_relics
```
`out_dir` defaults to `<project>/site_structures`.

### How every structure script works
1. `reset_scene()`, then `P = points()` reads the CSV and `pal = palette()` makes the materials.
2. `x, y, rot = loc_of("B17")` gets the position and rotation from the CSV.
3. `top = collection("PWM_B17_GunEmplacement")`: **the top collection must start with `PWM_`** (or your project prefix). That prefix is what the assembler links.
4. `rt = root(top, "B17_…_Root", x, y, rot)`: a root empty at the surveyed position. **Its z comes from `terrain.z_model`**, so the structure sits on the ground.
5. Geometry is built in the root's local coordinates using `Part`, which merges many primitives into **one mesh per material** (fast, few objects):
   ```python
   p = Part(top, "B05_Posts", pal["timber"], rt)
   p.boxz((0.2, 0.2, 6.0), (1.4, 1.4, 0))   # box standing on z=0
   p.cyl(0.1, 1.0, (0, 0, 6)); p.beam(a, b, w); p.rod(a, b, r); p.prism(pts_xz, depth); p.ring(...)
   p.done()
   ```
   Other helpers: `text()` for signs, `gable_roof()`, `gable_ends()`, `instance()` and `append_mesh()` (reuse meshes from other files), and `drape(objects)` for long objects like the walkway, whose vertices each get the terrain height.
6. **Materials** are procedural (`NM()` = noise + colour ramp + bump, in object space, no UVs needed), with colours from the survey palette section: weathered concrete, brick, rubble, timber, camouflage, zinc roof, teal render, and others. Look shader nodes up by type, never by name.
7. `finish(top, path, label)` marks the collection as an asset, packs, and saves. It refuses to overwrite.

### Accuracy tiers (use different detail levels)
| Tier | Source | Detail |
|---|---|---|
| Surveyed (B) | Street View + photos | Detailed models from the description; ±3–6 m |
| Satellite (S) | roofs only | Massing blocks with roofs (`block_building`) |
| Sketch (R/F) | sketch map ±30 m | Typed placeholders chosen by keyword in the label (pillbox, tunnel portal, gun bay, colonnade barrack, water tank, jetty, …) plus a standard interpretation board |

### Hero structures (hand-modelled)
The gate and the entrance plaza were modelled interactively through **Blender MCP** while looking at Street View, then saved in the same frame (origin = O). Their top collections are `WarMuseumEntrance` and `WarMuseumEntrance2`; these names are listed explicitly in `assemble_sitemap.py`. Poly Haven assets (plants, props) were imported and **baked to plain meshes**. Rigged or geometry-node assets crashed Blender, so don't keep rigs or node groups.

### Check every structure
```bash
"$BLENDER" -b site_structures/<file>.blend --python tools/render_check.py -- museum_survey/renders/<name>.png
"$BLENDER" -b site_structures/<file>.blend --python tools/render_focus.py -- museum_survey/renders R30_ R36_
```
Look at the PNG and compare it with the screenshots, then fix and rebuild. This render → look → fix loop is what made the models match.

## 8. Step 7: Vegetation from Poly Haven (`tools/build_vegetation.py`)

```bash
"$BLENDER" -b --factory-startup --python tools/build_vegetation.py -- site_structures/penang_war_museum_V_vegetation.blend
```
1. **Source meshes:** appended from the entrance-plaza file, where they were already imported and baked. These are Island Tree 02, Pachira, Shrub 04, Fern 02, Calathea and Anthurium. For a new site, import the Poly Haven models first (Blender MCP `import_asset`, or download the .blend from polyhaven.com) into any file and point `SRC` and `NAMES` at it.
2. **Far LOD tree:** plain decimation destroys leaf cards, so the script instead:
   - finds leaf-card islands (faces whose material name contains "leaves"),
   - keeps 30 % of them, each scaled ×1.45 about its centre, and deletes the rest,
   - decimates only the trunk and branch faces (ratio 0.15).
   The full tree has 316 k faces; the far tree has 87 k and still looks leafy.
3. **Exclusion zones** from the CSV:
   - every surveyed or satellite footprint + 4 m,
   - every sketch relic as a 9.5 × 5 m box at the sketch rotation,
   - the entrance zones and the approach road,
   - within 5.5 m of the walkway,
   - below sea level + 4 m.
4. **Trees:** a jittered grid with 12.5 m spacing over the site bounds, kept with probability 0.82. Trees within 45 m of a visitor point use the **full mesh**; others use the **far LOD**. Scale is 2.3–3.6 with random rotation and slight tilt, and each tree is seated at `ground_z − 0.15`.
5. **Understory:** 5000 random samples, kept between 2.8 and 22 m from visitor areas, with density falling off with distance from the paths.
6. PWM result: 41 near + 363 far trees and 150 understory plants.

For a new site: change the bounds `X0, X1, Y0, Y1`, the entrance and road zones, and the species list. Use a different `random.seed` for a different layout.

## 9. Step 8: Assemble the site map (`tools/assemble_sitemap.py`)

```bash
mv penang_war_museum_sitemap.blend /some/backup/      # the script refuses to overwrite
"$BLENDER" -b --factory-startup --python museum_survey/tools/assemble_sitemap.py -- penang_war_museum_sitemap.blend
```
What it does, in order:
1. **Saves first**, so library paths can be relative.
2. **Links** the two hand-modelled entrance collections by name, then every other `site_structures/*.blend`'s `PWM_*` collections. It skips `PB1`/`PB2` (stand-alone pillbox studies) and files already linked. Each collection becomes a **collection-instance empty at (0, 0, 0)**; no alignment is needed because every file shares origin O.
3. **Terrain mesh:**
   - a 4 m grid (PWM: x −450…350, y −250…330, so 201 × 146 vertices) with heights from `height(x, y)`,
   - heights = `z_model`, **flattened into pads** under every footprint (+1 m) and the entrance areas, and along the walkway (smoothstep blend over 6 m), so buildings never float or sink.
4. **Satellite texture:**
   - two UV maps computed from the georeferencing in step 3 (`UV_SAT07`, `UV_SAT01`),
   - a vertex-colour mask that uses the high-resolution image inside its crop and the context image outside,
   - Diffuse + 0.55 Emission, so the imagery reads under any light.
5. **Sea plane** at `SEA_Z + 0.3`.
6. Lifts the flat-built `WarMuseumEntrance2` to the plaza ground height.
7. Adds the origin marker, the sun, and three cameras: `Cam_TopDown_NorthUp` (orthographic, rotated 180° so north is up), `Cam_Oblique_FromNorthEast` and `Cam_Oblique_FromSea_SouthEast`. Also adds the world colour and AgX view transform, then packs and saves.

It prints `LINKED …` for each file, then `TERRAIN …` and `SAVED …`. The whole run takes about 2 s.

## 12. Adapting to a new place: checklist for an agent

Example: **Kellis Castle, Batu Gajah, Perak** (about 4.47 N, 101.08 E).
- It's an unfinished mansion ruin on a hill beside the Kinta River, with lawns and scattered trees.
- **Hero structure:** the castle itself. Model it by hand with Blender MCP from Street View and visitor photos, like the PWM gate.
- **Other structures:** the smaller buildings, paths and riverbank can go through `build_structures.py`.
- **Terrain:** much of the ground is open lawn, so the canopy correction there is near 0 m rather than −10 m.
- **Origin O:** the entrance gate or the ticket counter is a good choice.


1. **Make a project folder** next to the worked example, e.g. `~/Desktop/blender/kellis_castle/`, with `site_structures/` and `kellis_castle_survey/tools/`. Copy the scripts from `penang_war_museum/museum_survey/tools/` (not the `.json` data or `sketch.jpg`, which belong to Penang). Rename the `PWM_` prefix (e.g. `KC_`) and the file names: search for `penang_war_museum`, `museum_survey`, `PWM_` and `WarMuseumEntrance`. The scripts find files relative to their own folder, so the `<site>/<site>_survey/tools/` layout must stay the same depth.
2. **Choose origin O** at a recognisable ground point near the entrance. Compute `KE = 111320·cos(lat)` and `KN ≈ 111132 − 559.8·cos(2·lat)` (≈ 110 574 near the equator, ≈ 111 230 at 45°). Write the frame at the top of the survey.
3. **Survey** (step 1): walk Street View and save `P*` screenshots with lat/lon/heading/altitude in the names; take `SAT*` captures at known zoom levels; collect any official or sketch maps (`REF*`). Write the survey markdown with a master table.
4. **Calibrate the screenshot scale** for your window size (step 2).
5. **Edit `fit.py`** with control points if there's a sketch map; otherwise skip it and leave `SK` empty.
6. **Edit the lists in `make_sitemap.py`** (`S`, `WALKWAY`, `SV_PATH`, `SK`, `SATS`, map bounds `EMIN…NMAX`), then run it. Check the SVG against the satellite imagery.
7. **Run `fetch_srtm.py`** with your origin and bounds. Put your Street View altitudes in `terrain.py` `SV`, set `DEFAULT_CORR` (≈ −10 m in forest, ≈ 0 m in open or urban ground), then run `terrain.py` and check the residuals.
8. **Write a builder function** per structure group in `build_structures.py`, using `loc_of()`, `root()`, `Part`, `palette()` and `finish()`. Start with massing, render-check, then add detail from the survey descriptions.
9. **Vegetation:** import Poly Haven species that fit the climate, bake them to meshes, set `SRC`, `NAMES`, bounds and zones, then run.
10. **Edit `assemble_sitemap.py`:** the `LINK` list for hand-made files, `SKIP`, terrain bounds `X0…Y1`, the `SATS` dictionary, extra pads, and camera positions. Then run it.
11. **Render, look, fix, repeat**, then document in the survey (section 9) and the gap checklist.

### Lessons learned (avoid these traps)
- Plain decimation turns leafy trees into bare sticks. Thin the leaf-card islands instead (step 7).
- Poly Haven assets with rigs or geometry nodes can crash background Blender. Load meshes with `bpy.data.libraries.load` and keep plain meshes only.
- Set the **parent before the location**, or children end up at the world origin.
- Boolean operations on curved concrete failed. Build annulus or apron shapes directly as bmesh vertex rings.
- When files are moved, linked libraries break unless paths are relative. Check with a short script that prints `bpy.data.libraries` and whether each path exists.
- SRTM under forest is 5–12 m too high. Always calibrate against ground truth.
- Sketch maps distort by up to 30 m. Label sketch-derived positions as approximate and replace them with GPS when possible.
- Keep **one CSV** as the source of positions. Don't hard-code coordinates in the model scripts.
- Never overwrite: back up, then rebuild. Never edit a .blend the user has open; work in background Blender on copies.
